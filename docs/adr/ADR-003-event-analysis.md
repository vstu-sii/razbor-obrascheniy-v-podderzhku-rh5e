# ADR-003: очередь автоматического разбора
Дата: 23.10.2026. Проект LAB02 на основе Product UC-01–04.

## Решение
Backend принимает через helpdesk adapter события ticket.created и customer.message_received. Подпись, тип, размер и права интеграции проверяются до записи. Событие и задача сохраняются одной транзакцией PostgreSQL. Подтверждение отправителю возвращается после commit.

Очередь MVP хранится в PostgreSQL. Исполнитель входит в backend. Получение задачи использует SKIP LOCKED и lease. Для тикета выполняется одна задача и ожидает не больше одной задачи последней версии. Повторные события дедуплицируются по event_id и паре ticket_id/input_version.

UI читает queued/running/ready/manual_review и готовую карточку. Новая версия делает старый результат устаревшим. Сохранение результата и подтверждение решения сверяют current_input_version под блокировкой строки тикета. История предложений и review сохраняется.

Конечные MAX_RUNNING, MAX_PENDING, MODEL_REQUESTS_PER_MINUTE и TOKEN_BUDGET задаются конфигурацией по квотам среды. При насыщении возвращается retryable 503 без подтверждения события. Отправитель хранит событие для повторной доставки. Изменение статуса, заметка, просмотр и review не создают разбор.

Общий deadline задачи 55 секунд, максимум два вызова модели. Попытка и резерв записываются до сети. Перезапуск не обнуляет расход. Истёкший lease возвращает задачу только в пределах оставшегося бюджета. После лимита используется manual_review. Отправку и назначение подтверждает оператор.

## Альтернативы
Синхронный вызов модели из webhook задерживает подтверждение события. Отдельный брокер требует дополнительного сервиса и outbox. Для учебного MVP выбрана существующая PostgreSQL с транзакционной записью.

## Цена решения
База дополнительно обслуживает очередь, lease и индексы. Нужны очистка событий, контроль возраста задач и регулирование конкуренции. Рост нагрузки потребует отдельного брокера и outbox. Конечная очередь требует повторной доставки источником.
## Техническое уточнение review 25.10.2026

Статус: Product UC интегрированы в main; реализация очереди остаётся проектом
LAB02. Технические исправления Delivery требуют review, не выдают принятие всей команды.
Входящий Event ingress — отдельный ACL, исходящий Helpdesk adapter выполняет
чтение/подтверждённые действия. Это устраняет цикл зависимостей API↔adapter.
Ценой становятся дополнительный процесс и отдельный контракт; альтернатива —
сознательно разрешённый цикл, но она противоречит принятой проверке acyclic.

SQL содержит составной FK событие/тикет/версия, occurred_at и журнал резервов
каждой попытки. Блокировка строки тикета при создании review запрещает решение
по устаревшей версии. Сохранение результата требует такой же блокировки.
Attempts и записи model_attempt обновляются одной транзакцией до сети.
Два вызова — общий лимит всех рестартов, а не два вызова на каждую доставку.
Вложенные повторы AI-адаптера входят в тот же бюджет: внешний retry loop
исполнителя не должен умножать их. AI PR #22 ещё не объединён; это зависимость.

Параметры конечной очереди перечислены в .env.example; учебные defaults не
являются измеренной пропускной способностью. Для глобальных лимитов требуется
транзакционная координация всех исполнителей, а не счётчик в памяти процесса.
При перегрузке 503 не записывает/не подтверждает событие; уже известный дубль
подтверждается без создания новой задачи даже при заполненной очереди.
Срок хранения/очистка dedup-записей должны сохранять окно повторной доставки.

Compose запускает health-заглушки всех C4-границ и применяет обе SQL-схемы.
Он не реализует webhook, lease, квоты или фоновые вызовы: это следующий runtime
этап, который нельзя считать выполненным по существованию контейнера.
