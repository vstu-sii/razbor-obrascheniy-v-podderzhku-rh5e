# ADR-004: квоты, бесплатная деградация и проверяемый выпуск

Дата: 27.10.2026. Статус: техническое решение Delivery реализовано в task-ветке,
нужно cross-role review, production подключение ещё не подтверждено.

## Решение

Квоты закрепляются за actor из аутентификации, не из текста клиента. Admission,
daily LLM calls и резерв токенов хранятся в PostgreSQL/SQLite с общей транзакцией
очереди. Запись попытки и резерва производится до сети. Дубликат события не
порождает новый расход. UTC сутки и lifetime safety cap различаются явно.

Когда платная квота исчерпана, выбирается существующий бесплатный extractive
baseline. Ограничение выбирает приложение и проверяет AI API по сохранённому
claim. Даже service token не разрешает повторить платный claim или поменять
зарезервированный вход. Модель предлагает карточку; прав на отправку/аккаунты нет.

Выпуск привязан к полному SHA, quality gates и сборке, подтверждается revision
в /health. Откат production требует совместимого ранее зелёного ancestor.
JSON logs не содержат тексты/ключи; HTTP и model.attempt связаны W3C trace ID,
OTLP поступает в Tempo, логи — в Loki, метрики — в Prometheus/Grafana.

## Альтернативы

Счётчик в памяти не переживает рестарт и умножает бюджет на число worker.
Другая платная модель при исчерпанной квоте продолжает расход и требует
новых измерений AI Engineer. Неограниченный retry и ACK до commit недопустимы.
Один HTTP 200 старого процесса не доказывает размещение нового кода.

## Цена решения

Глобальный DB lock ограничивает throughput MVP. Резерв может существенно
превышать измеренный расход; неизвестные попытки консервативно не возмещаются.
Extractive хуже LLM и всегда требует проверки оператором, улучшение качества
не заявляется. Количество журналов растёт; telemetry retention ограничен,
очистку делового audit/квот нужно проектировать с сохранением dedup окна.
Одноузловый monitoring локален; Render Free требует внешнего monitoring
endpoint и не равен Compose по физической топологии/доступности.
