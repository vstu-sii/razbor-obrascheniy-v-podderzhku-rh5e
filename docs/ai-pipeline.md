# AI-пайплайн LAB02

09.10.2026. Роль AI Engineer. Архитектурный проект для русскоязычного помощника оператора B2B SaaS: [PlantUML](ai-pipeline.puml), [OpenAPI](../api/openapi.yaml), [решение по модели](model-candidates.md), [эксперимент](experiments/lab2.md).

## Вход и контекст

Backend проверяет сервисную авторизацию и права оператора на тикет, удаляет секреты и лишние персональные данные. Вход AI-API: request_id, непрозрачный ticket_ref, ticket_text, разрешённая history и неизменяемая kb_version. Предел тела 65536 UTF-8 байт, до 10000 символов обращения, до 50 сообщений истории; остальные ограничения — в OpenAPI. Ключ модели хранится в адаптере и никогда не передаётся в промпт.

Knowledge service владеет отдельной БЗ. AI сначала отбирает approved статьи точной версии данного сервиса, затем BM25 ищет по всему разрешённому корпусу и выдаёт top-3. Поля ожидаемого ответа и подсказки разметки не используются для baseline. Модель видит только обезличенный тикет, историю и снимки найденных статей {source_id,version,title,excerpt}. Наличие похожей статьи не разрешает уверенный ответ.

Тикет, история и KB — недоверенные данные. Их инструкции не изменяют системные правила. Модель не имеет прямого доступа к БД, Интернету, helpdesk, отправке, назначению или изменению тикета. В эксперименте все тексты синтетические.

## Модельный адаптер и контроль

Два проверенных экспериментальных маршрута: openai/gpt-5.6-sol через https://apimira.com/v1 и ministral-14b-2512 через https://api.mistral.ai/v1. В сравнении одинаковые system prompt, вход, schema и предел 1000 output токенов; Sol использует max_completion_tokens и reasoning_effort=low, Mistral — max_tokens. Эти параметры отличаются по протоколу поставщиков и фиксируются отдельно.

ApiMira не принимает response_format, поэтому общий transport — ровно один forced вызов propose_card с аргументами JSON. propose_card — исключительно формат данных; никакой код функции не исполняется. В декларации функции упрощены условия allOf, но полный независимый серверный валидатор проверяет их после ответа. Поддержка tools не означает гарантированную валидность результата. [ApiMira](https://apimira.com/docs), [Mistral Chat API](https://docs.mistral.ai/api/endpoint/chat).

Последовательно проверяются ровно один разрешённый tool call, завершённость ответа, JSON, полная схема, точный request_id и provenance каждого evidence. source_id/version/title/excerpt должны дословно совпадать с реально переданным фрагментом нужной версии. Ответ answer требует непустого источника и текста; clarify требует недостающего факта и вопроса; escalate — без клиентского черновика. not_analyzed не может сочетаться с answer. needs_human_review всегда true.

Проверка происхождения цитаты необходима, но не доказывает её смысловую поддержку или правильную политику риска. Оператор сверяет факты, черновик и маршрут с исходным тикетом и источником. При утечке, чужих данных, неподтверждённых полномочиях и массовом сбое нужны отдельные проверенные правила эскалации; такой серверный risk gate пока не реализован в эксперименте.

Невалидный JSON/schema/ID/источник, незавершённый ответ или превышение deadline → not_analyzed/escalate, без known_facts, evidence и draft_reply, с warning и ручным next_step. Backend сохраняет предложение и immutable source snapshots отдельно от operator_review. Только после явного решения человека и проверки прав backend обращается к helpdesk adapter. UC-04 — действие оператора, а не новый inference.

## Бюджет, доступность и задержка

Итоговый общий лимит эксперимента — 20 ₽, включая ранее учтённые расходы/резервы. Для программного cap используется условная конверсия 100 ₽/$ → $0.20; это не актуальная валютная котировка. До каждого запроса или пары проверяется общий расход плюс резерв. Вход оценивается по UTF-8 размеру payload, выход — по max tokens; точный токенизатор ещё нужен для runtime. Резерв записывается до сетевого вызова; прерывание не приводит к бесплатному повтору.

Стоимость после ответа вычисляется по usage и снимку тарифов; для Sol по возможности сверяется с account usage по completion ID + модели + token counts. Для Mistral без account invoice это оценка по официальному тарифу; скидка кэша не предполагается без подтверждения. Тайм-ауты с неизвестным списанием сохраняют резерв. Невозможность принять полный контекст → ручной разбор; важную историю молча не отрезать.

Целевой runtime: до 8000 input + 2000 output, единый deadline 55 с и максимум два модельных вызова суммарно с общим бюджетом. Текущий эксперимент: один вызов на кейс/маршрут, connect/read timeout=(10,55). Это не строгий wall-clock deadline; превышение измеренных 55 с делает карточку непригодной. Отдельная проверка доступности генерации не является оценкой качества.

## Ошибки и логирование

400 — некорректный JSON; 422 — нарушение входной схемы; 413 — тело сверх 64 KiB; 401 — service bearer auth. Недоступные модель/БЗ → 503 ErrorResponse(message,retryable); backend показывает ручной разбор. Индивидуальная непригодная карточка → успешный ответ с not_analyzed/escalate. Не возвращать stacktrace, ключи и подробности поставщика клиенту. /health — техническая готовность, не гарантия анализа.

Production логи: request_id, версия БЗ/источников, hash промпта/схемы, requested/returned model, mode/status, gate code, usage, цена и latency. Текст обращений, ключи и персональные данные не логируются. Только эксперимент сохраняет синтетические raw/final cards для проверяемого отчёта; доступ и срок хранения реальных snapshots определяет backend/Quality.

## Модель данных и граница Delivery

[ERD и таблица соответствия контракту](architecture/README.md) фиксируют тикет, статью БЗ со статусом/версией, предложение, снимки evidence и отдельное решение оператора. Diagram/SQL ownership остаётся у Delivery. Использована без изменения опубликованная ERD Delivery 9aa47a2; это общая схема, а не новая миграция AI Engineer.

Проверено соответствие request_id/kb_version/evidence и сущностей хранения. До runtime интеграции вместе с Delivery согласовать минимальную длину history.text, HealthResponse без mode, типизированные ошибки/422, service auth и общий deadline. Это контракт для параллельной работы, не заявление о командной подписи или готовом HTTP-сервисе.
