# AI-пайплайн разбора обращений

Статус: проект Lab 2 для согласования с Product/VO, Delivery и Quality & Safety. Артефакт подготовлен по требованиям [Lab 2 для роли AI Engineer](https://sii.sergeivolchkov.ru/labs/lab2#roles) и развивает выбранный в Lab 1 подход RAG + Structured Outputs из [`research.md`](research.md).

Схема последовательности: [`ai-pipeline.puml`](ai-pipeline.puml). Внешний контракт: [`api/openapi.yaml`](../api/openapi.yaml).

## Цель и граница ответственности

AI API готовит только **предложение** карточки разбора: режим `answer`, `clarify` или `escalate`, краткую суть, факты, недостающие данные, основания и черновик. Он не отправляет сообщение клиенту, не назначает исполнителя и не изменяет тикет. Любое внешнее действие выполняется backend/helpdesk только после явного решения оператора.

Такое ограничение уменьшает последствия ошибочного или атакованного вывода модели. Оно соответствует рекомендации минимизировать функциональность, разрешения и автономность LLM-системы из [OWASP LLM06:2025 Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/).

## Последовательность обработки

1. Backend принимает тикет из helpdesk, проверяет полномочия оператора, размер, типы данных и правила обезличивания.
2. Backend вызывает `POST /v1/analyze`, передавая `request_id`, непрозрачный `ticket_ref`, текст обращения, разрешённую историю и требуемую версию БЗ.
3. AI API считает текст обращения, историю и документы БЗ недоверенными данными. Инструкции внутри них не меняют системные правила. Prompt injection является отдельным классом риска согласно [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).
4. Retrieval ищет не более трёх фрагментов только среди источников со статусом `approved` и заданной версией. Каждый фрагмент содержит `source_id`, `version`, `title` и `excerpt`.
5. Модель получает минимальный контекст: системную инструкцию, JSON Schema карточки, обращение, релевантную историю и отфильтрованные фрагменты БЗ. Выбранный кандидат поддерживает Structured Outputs по [официальной документации OpenAI](https://developers.openai.com/api/docs/models/gpt-5.6-sol).
6. Детерминированный валидатор проверяет JSON Schema, перечисления, длины и ссылки на evidence. Для режима `answer` обязателен хотя бы один разрешённый источник.
7. Policy gate запрещает `answer`, если нет основания, версии конфликтуют, требуется доступ к чужому аккаунту или совет может раскрыть пароль, токен либо платёжные данные.
8. При невалидном результате разрешён один повтор с тем же безопасным контекстом. Повторная ошибка, timeout или недоступная БЗ дают `status=not_analyzed`, `mode=escalate` и ручной маршрут.
9. Backend сохраняет исходное предложение отдельно от решения оператора. Оператор принимает, редактирует или отклоняет карточку; только после этого внешний интерфейс может отправить ответ или передать тикет.

## Стадии и наблюдаемость

| Стадия | Вход | Выход | Безопасный отказ | Метрики |
| --- | --- | --- | --- | --- |
| Валидация запроса | тикет, история, версия БЗ | нормализованный запрос | `400`/`413`, AI не вызывается | размер, причина отказа |
| Retrieval | запрос и `kb_version` | до 3 approved-фрагментов | пустой список evidence | Recall@3, latency |
| LLM | данные + evidence + схема | JSON-предложение | отказ/невалидный JSON | input/output tokens, latency, стоимость |
| Schema validator | JSON | типизированная карточка | один retry | schema-valid rate, retry count |
| Policy gate | карточка + разрешённые source ID | `answer/clarify/escalate` | `escalate`/manual review | false-answer count, причины блокировки |
| Human review | предложение + исходник | accepted/edited/rejected | ручная обработка | доля пригодных карточек |

В техническом журнале без полного сырого текста клиента сохраняются `request_id`, версии модели, prompt и БЗ, ID источников, режим, результаты validator/policy gate, число токенов, стоимость и длительность стадий. Срок хранения и роли доступа должны быть согласованы Delivery и Quality & Safety до production.

## Границы контекста

Модель видит только текст текущего обращения, отобранную историю, минимальные разрешённые поля и approved-фрагменты БЗ. Она не видит пароли, API-ключи, полные платёжные реквизиты, чужие тикеты, секреты сервиса, произвольный Интернет и инструменты записи.

Проектный бюджет одного вызова — до 2200 входных и 500 выходных токенов; максимум один полный повтор. Происхождение лимитов и расчёт находятся в [`model-candidates.md`](model-candidates.md#токен-бюджет-одного-разбора) и ноутбуке Lab 1.

## Соответствие командным use cases

| Сценарий | Поведение AI | Проверяемое ограничение |
| --- | --- | --- |
| UC-01: обоснованный ответ | `answer`, черновик и evidence | каждое существенное утверждение проверяется по источнику; отправляет оператор |
| UC-02: уточнение | `clarify`, пробелы и один конкретный вопрос | не запрашивать уже известное и чувствительные данные |
| UC-03: передача специалисту | `escalate`, факты и причина | AI не выбирает адресата и не меняет назначение тикета |
| UC-04: исправление/отклонение | сохраняется исходное предложение | отклонение не вызывает внешнего действия |

Категории и режимы синхронизированы с проектом команды: `access`, `payment`, `settings`, `integrations`, `product_error`, `other` и `answer`, `clarify`, `escalate`.

## Что ещё требуется проверить

Текущая схема является проектом, а не доказательством качества. До окончательного выбора модели нужны одинаковые прогоны GPT-5.6 Sol и Mistral Medium 3.5 на утверждённом golden dataset: schema-valid rate, пригодность карточки, false `answer`, Recall@3, p50/p95, полная стоимость и safety-набор. Два локальных спайка Lab 2 проверяют только детерминированные guardrails и описаны в [`docs/experiments/lab2.md`](experiments/lab2.md).
