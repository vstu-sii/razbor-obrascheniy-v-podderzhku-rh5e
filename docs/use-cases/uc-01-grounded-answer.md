# UC-01 — Подготовить обоснованный ответ

**Актёр:** оператор первой линии. **Цель:** ответить на типовой текстовый вопрос с проверяемым основанием. **Контекст:** открыто обращение русскоязычного B2B SaaS; у оператора есть право видеть историю и утверждённую базу знаний. Отправка ответа остаётся действием оператора.

**Предусловия:** система поддержки передала событие о новом обращении; текст и история доступны; в утверждённом источнике есть ответ на вопрос; внешние действия от имени клиента не требуются.

## Основной сценарий

1. Система поддержки передаёт событие о создании обращения. Система автоматически ставит разбор в очередь.
2. Система готовит карточку и показывает статус `в очереди`, `разбирается`, `готово` или `нужна ручная проверка`.
3. Когда разбор готов, карточка появляется в очереди оператора с сутью, известными фактами, категорией, срочностью и её основанием, источниками, недостающими данными и следующим шагом.
4. При достаточных основаниях система предлагает режим `answer` и черновик, привязанный к конкретным источникам. Она не отправляет сообщение.
5. Оператор открывает источники, сверяет факты с историей, при необходимости правит черновик.
6. Оператор подтверждает отправку в интерфейсе поддержки. Перед подтверждением система сверяет версию карточки с актуальной версией обращения.
7. Интерфейс показывает факт отправки и сохраняет использованный оператором текст и контекст решения.

**Результат:** клиент получает только подтверждённый оператором ответ; оператор может показать, на каких источниках он основан.

**Альтернативы:** если очередь занята, обращение остаётся видимым со статусом ожидания, событие не теряется и не запускает параллельные разборы одной версии обращения. Если пришло новое сообщение клиента до начала разбора, ожидающий разбор заменяется разбором актуальной версии. Если сообщение пришло во время разбора, готовая карточка помечается устаревшей и система ставит одну задачу для новой версии. Подтверждение устаревшего предложения блокируется, ранее сохранённые решения остаются в истории. Повторная доставка того же события не создаёт новую задачу. Временный сбой получает ограниченное число повторов; после них карточка видна оператору как требующая ручной проверки. Если источник подтверждает только часть обращения, неподтверждённая часть явно отмечается; полный ответ в режиме `answer` не предлагается. Оператор не отправляет такой черновик и переходит к [UC-02](uc-02-clarification.md) или [UC-03](uc-03-escalation.md). Если черновик неверен, применяется [UC-04](uc-04-review-rejection.md). Если поиск недоступен, система явно сообщает об отсутствии основания и не предлагает уверенный ответ.

**Правило приёмки:** новый тикет автоматически получает задачу разбора без нажатия оператором кнопки запуска. Для тикета одновременно выполняется не больше одного разбора. Новая версия ожидает завершения текущего разбора. Повторное событие не создаёт дубликат. Оператор видит состояния ожидания, разбора, готовой карточки и ошибки. Нельзя получить отправленное AI сообщение без явного действия оператора; каждый существенный факт черновика можно проверить по показанному источнику или истории. Численные ограничения очереди, параллельности и задержки задаются Delivery после оценки мощности, а не считаются уже измеренными.
