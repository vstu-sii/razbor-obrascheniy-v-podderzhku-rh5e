# PRD v3: автоматический разбор обращений в поддержку

Редакция LAB04 от 29.10.2026 (с сохранением решений LAB03). Основание: PRD LAB01, UC LAB02, реальные ответы
baseline и проверка локального прототипа участником. Изменение P-009 переводит
первичный запуск на событие создания обращения. Повторное прохождение UC после изменения подтверждено участником 23.10.2026. Исходный PRD LAB01
сохраняется в истории Git. Требования курса: [LAB04](https://sii.sergeivolchkov.ru/labs/lab4).

## Пользователь и проблема

Оператор первой линии русскоязычного B2B SaaS разбирает текстовые обращения
о доступе, оплате, настройках, интеграциях и ошибках продукта. Требуется быстрее
восстановить контекст, найти основание ответа и определить следующий шаг.
Портрет команды 3–15 операторов с 100–500 обращениями в день остаётся гипотезой
сегмента из LAB01. Собственные интервью не добавлялись, спрос и экономический
эффект на реальном потоке не подтверждены.

## Объём учебного прототипа

Один условный сервис, синтетические тексты, история и шесть учебных статей БЗ v1.
Событие создания обращения автоматически ставит разбор в очередь. Оператор
открывает готовую карточку либо видит её состояние ожидания или обработки.
Внутренние изменения карточки оператором и повторная доставка события сами по
себе не запускают новый разбор.
Система предлагает карточку с краткой сутью, категорией, срочностью и её
обоснованием, известными фактами, недостающими сведениями, источниками,
предупреждениями, следующим шагом и черновиком, когда он допустим.
Оператор принимает, исправляет или отклоняет предложение. Исходная карточка
остаётся неизменной, каждое решение сохраняется отдельно с автором, временем,
причиной и итоговым текстом. Записи сохраняются при перезапуске приложения.

Подтверждение в учебном интерфейсе сохраняет решение. Оно не отправляет
сообщение клиенту, не выдаёт доступ и не назначает исполнителя helpdesk.
Полный сценарий LAB02 с внешней отправкой/назначением требует будущего адаптера.
Вложения, автоматические внешние действия, реальные персональные данные, индивидуальные
права организаций и промышленная нагрузка остаются вне учебной версии.

## Требования к поведению

| ID | Требование | Приёмка |
| --- | --- | --- |
| R-01 | answer допустим при достаточной актуальной статье | Весь answer совпадает с актуальным approved-фрагментом. Применение статьи проверяет оператор |
| R-02 | clarify содержит конкретный пробел и непустой вопрос | Не запрашиваются повторно известные сведения, пароль, значение токена, код 2FA или платёжный секрет |
| R-03 | Рискованный случай передаётся оператору через escalate | Черновик пуст, причина передачи понятна, внешнее действие не объявлено выполненным |
| R-04 | Отсутствующая версия БЗ блокируется до вызова модели | escalate, not_analyzed, предупреждение о версии, ноль LLM-вызовов |
| R-05 | Предложение и решение оператора разделены | Исправление не меняет исходную карточку, rejected имеет пустой итоговый текст |
| R-06 | Оператор видит все сведения, необходимые для проверки | UI показывает факты, пробелы, срочность, предупреждения, цитаты и сохранённые решения |
| R-07 | Отказ генерации виден пользователю | Ручной fallback не выдаётся за успешный ответ модели и не улучшает её метрики |
| R-08 | Результаты можно восстановить после перезапуска | Карточка и отдельные решения читаются из БД после повторного открытия |
| R-09 | Текст клиента и статьи являются данными | Команды обхода, передачи секретов и внешних действий не выполняются |
| R-10 | Результаты эксперимента привязаны к конфигурации | Сохранены версии модели, инструкций, набора, исходные ответы, попытки, токены и задержка |
| R-11 | Новое обращение автоматически ставится на разбор | Оператору не нужно нажимать кнопку первичного разбора. До результата видны состояния очереди и обработки, затем появляется готовая карточка |
| R-12 | Одно событие создаёт не более одной задачи на версию обращения | Повторная доставка события не запускает дубликат. Изменение статуса или заметка оператора не считается новым входом клиента |
| R-13 | Очередь и запуск ограничивают нагрузку | Заданы пределы параллельных задач, ожидающей очереди, частоты вызовов, бюджета токенов и повторов. При насыщении задача сохраняется в ожидании, оператор видит статус, событие не теряется молча |
| R-14 | Новое сообщение клиента запускает разбор актуальной версии | Ожидающую задачу старой версии можно заменить новой. Если старая версия уже обрабатывается, её результат помечается устаревшим, подтверждение блокируется, а актуальная версия ожидает освобождения исполнителя |
| R-15 | Сбой автоматического разбора имеет конечный исход | После ограниченных повторов карточка получает статус ручной проверки и понятную причину. Ответ или внешнее действие не выполняются автоматически |

Вопрос клиента не доказывает совершённое действие. Отсутствие сообщения об
ошибке не доказывает отсутствие самой ошибки. Актуальная цитата подтверждает
её текст, но не все дополнительные утверждения модели. Приёмка JSON и смысловая
проверка считаются отдельно.

## Метрики и текущий результат

North Star сохраняется: доля карточек, с которыми оператор может продолжить
работу без повторного чтения всей истории, при верных фактах и обоснованном шаге.
На реальном потоке она пока не измерена. Содержательная рубрика Quality на
учебном наборе служит диагностикой, её нельзя автоматически приравнять к North Star.

Текущий LAB04 v2.1: 36 новых HTTP-ответов и два отказа до генерации,
38 групп / 49 записей. Raw LLM: режим 33/38, категория 33/38. Текущая система
при replay тех же ответов: режим 35/38, категория 36/38, Macro-F1 0,9310,
false answer 0/28, схема/gate 38/38. Системная коррекция категории не меняет
сохранённую raw-карточку. CI проверяет ≥90% режима и категории, ≤2% false
answer, 100% схемы и gate на development-наборе. 0/28 недостаточно для
статистического доказательства промышленного предела 2%.

Предложения LAB01 для будущего пилота (p95 всего пути ≤60с, удобство ≥85%,
бюджет ≤5 ₽) не объявляются достигнутыми. Нужны реальный поток, отдельный
набор, тариф и человеческая рубрика. Тесты событийной доставки и очереди
измеряются отдельно от качества модели: EVT-01–14 пройдены на SQLite и PG.

## Решения после проверки

Для учебного демо принимаются локальный запуск и сохранение решения без отправки.
Отсутствующая версия БЗ стала проверяемым системным ограничением после живого
случая с ошибочным clarify. В UI добавлены данные карточки и журнал решений.
Операции с реальными клиентами требуют отдельной приёмки, исправления P0,
индивидуальных прав и адаптера. Согласованный со слов участника план команды
на спринт 4 находится в `docs/iteration-notes.md` после публикации материалов.
UC-01–04 повторно пройдены после уточнения способа запуска. Подтверждение участника зафиксировано 23.10.2026. Содержание карточки, проверка источников и сохранение решения оператора соответствуют прежним сценариям.
