# Записка о первых пробах — Lab 1 / AI Engineer

## Что действительно было сделано

18.09.2026 в старой AI-ветке зафиксированы четыре потоковых API-вызова через OpenRouter, по одному на модель. Данные из исходных логов перенесены в [ноутбук](../../notebooks/lab1_prompt_experiments.ipynb): параметры, число токенов из API, время и полные видимые ответы. Исходные лог-файлы в этой папке не предоставлены, поэтому независимую повторную проверку их происхождения провести нельзя. Новых вызовов при этой переработке не делали.

Общий prompt `lab1-smoke-v1` не включал текст обращения, историю, статьи БЗ и реальную JSON Schema. Потоковый `max_tokens` был 1199, температура не задавалась. Замер времени выполнялся клиентским `llm_metrics.py`; сам скрипт и провайдерский биллинг не приложены. Поэтому опыт проверяет лишь поведение на пустом контексте и форму видимого ответа.

| Модель | Время | Input | Output | Наблюдение |
| --- | ---: | ---: | ---: | --- |
| `openai/gpt-5.6-sol` | 5,43 с | 214 | 252 | Валидный JSON с ожидаемыми полями; запросил недостающие данные и участие оператора |
| `mistralai/mistral-medium-3-5` | 1,34 с | 274 | 76 | Вернул текст, а не JSON |
| `qwen/qwen3.8-max` | 55,15 с | 283 | 2136 | JSON, но `operator_required=false` при отсутствии входных данных |
| `deepseek/deepseek-v4-pro` | 27,69 с | 243 | 1540 | JSON в Markdown-блоке с несовместимыми именами полей |

Это **четыре отдельных наблюдения**, не средние значения. В частности, 5,43 с для Sol не означает выполнение продуктового p95 ≤ 60 с. Цена в [сравнении моделей](../model-candidates.md) — расчёт по старым справочным ставкам, не фактическая сумма счёта.

## Что показано и чего ещё нет

Показано: модели различались по задержке, расходу и форме ответа на данном prompt. Не показано: точность категории и срочности, качество summary, полнота карточки, Recall@3, безопасность на реальных обращениях, стоимость законченного triage и пригодность для оператора. Без обращения и БЗ нельзя считать корректным ни предложенный ответ, ни выбор `answer / clarify / escalate` для продукта.

Новая версия PRD Product/VO требует AI-первую линию с подтверждением отправки оператором, шесть предварительных категорий и пригодную карточку как North Star. Поэтому последующий эксперимент должен измерять весь разбор, а не наличие JSON. Синтетические записи Quality показывают формат, но до двойной проверки не служат test-набором.

## План следующего эксперимента

1. Зафиксировать одну версию PRD, БЗ, словаря категорий, JSON Schema и prompt; выбрать не менее 10 проверенных примеров с `answer`, `clarify`, `escalate`, длинной историей, critical и safety-случаями. Реальные формулировки брать только с разрешением.
2. Сравнить ручной поиск, direct prompt и retrieval по одной версии источников. Для H4 Product отдельно сравнить Recall@3 объединённого поиска и поиска только по БЗ.
3. Основную модель и альтернативу прогнать минимум три раза на каждом примере с одинаковым входом и принудительной схемой. Фиксировать не только валидность JSON, но и содержательные ошибки.
4. Quality независимо оценивает обязательные факты, источники, недостающие данные, категорию, срочность, режим, маршрут, опасные рекомендации и пригодность карточки. Разногласия разрешаются до подсчёта итоговых метрик.
5. Сохранить для каждого вызова model/provider route, версии входа, токены, p50/p95 latency, timeout, фактическую цену провайдера, стоимость retrieval/embeddings и число повторов. Отчёт включает числители и знаменатели, а не только проценты.

Критерий решения: модель выбирается после измерения качества и стоимости на одном наборе и review Product/Quality. Текущий выбор Sol — только выбор кандидата для следующей проверки.
