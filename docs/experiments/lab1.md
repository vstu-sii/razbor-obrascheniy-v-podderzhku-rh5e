# Первые эксперименты

## Цель

Первый практический эксперимент сравнивает расход токенов, задержку и базовую пригодность формата ответа у четырёх облачных моделей. Это API smoke-тест перед основным сравнением direct prompt и RAG на 10 одинаковых golden-примерах.

## Методика

Дата запуска: 18.09.2026.

Провайдер: OpenRouter, OpenAI-compatible Chat Completions API, потоковый режим.

Параметры запуска:

- один запуск на модель;
- одинаковый базовый prompt версии `lab1-smoke-v1`;
- `max_tokens=1199`;
- temperature явно не задавалась;
- токены получены из поля `usage` API, а не оценены локальным токенизатором;
- время измерялось клиентским скриптом `llm_metrics.py` от начала запроса до завершения потока.

Безопасный шаблон команды, не содержащий ключ:

```bash
python3 llm_metrics.py \
  --base-url https://openrouter.ai/api/v1 \
  --api-key "$OPENROUTER_API_KEY" \
  --model openai/gpt-5.6-sol \
  --max-tokens 1199 \
  --show-completion
```

Для остальных запусков изменялся только идентификатор модели. Секретный API-ключ в репозиторий и ноутбук не добавляется.

### Расчётная стоимость

Для сопоставимости использованы ставки из [`docs/model-candidates.md`](../model-candidates.md):

`cost = input_tokens × input_price / 1 000 000 + output_tokens × output_price / 1 000 000`.

| Модель | Расчёт | Стоимость одного запуска |
| --- | --- | ---: |
| GPT-5.6 Sol | `214 × 4 / 1e6 + 252 × 20 / 1e6` | $0,005896 |
| Mistral Medium 3.5 | `274 × 1,5 / 1e6 + 76 × 7,5 / 1e6` | $0,000981 |
| Qwen3.8 Max | `283 × 2 / 1e6 + 2136 × 6 / 1e6` | $0,013382 |
| DeepSeek V4 Pro | `243 × 1,32 / 1e6 + 1540 × 3,96 / 1e6` | $0,006419 |

Это расчёт по справочным ставкам Artificial Analysis, а не фактический биллинг OpenRouter. Он не учитывает возможную наценку маршрута, округление, кэширование и скидки провайдера.

## Анализ

Mistral показал минимальные задержку, расход токенов и расчётную стоимость, но вернул prose вместо JSON. Без принудительной схемы этот ответ нельзя безопасно передать приложению.

GPT-5.6 Sol занял второе место по времени и расходу, при этом единственным сочетал быстрый ответ, сырой JSON со всеми 10 ожидаемыми полями и консервативное поведение: при отсутствии данных запросил уточнение и потребовал участие оператора.

Qwen также вернул сырой JSON со всеми ожидаемыми полями, но потратил в 5,19 раза больше токенов и отвечал в 10,16 раза дольше GPT. Кроме того, при отсутствии данных выставил `operator_required=false`, что требует отдельной проверки продуктовой логики.

DeepSeek потратил 1783 токена, а видимый ответ был коротким. Это указывает, что `completion_tokens` провайдера может включать внутренние reasoning-токены. Ответ дополнительно обёрнут в Markdown и использует русские ключи, поэтому без постобработки не соответствует ожидаемому API-контракту.

## Ограничения эксперимента

В prompt не были переданы текст обращения, история, фрагменты базы знаний и сама JSON Schema. Поэтому этот запуск не измеряет точность категории, срочности, retrieval, полноту карточки или соблюдение реальной схемы. Формулировка «10 ожидаемых полей» означает только ручную проверку набора ключей в полученном JSON.

Один запуск не позволяет вычислить p50/p95 и не отделяет стабильное поведение модели от колебаний маршрута OpenRouter. Различное число input-токенов при одинаковом тексте ожидаемо из-за разных токенизаторов моделей.

## Решение и следующий эксперимент

Для следующего этапа выбран `openai/gpt-5.6-sol`; `mistralai/mistral-medium-3-5` остаётся дешёвым резервным кандидатом.

Следующий эксперимент должен:

1. Передать фиксированную JSON Schema через `response_format`, а не только упомянуть её в prompt.
2. Прогнать обе модели на одних и тех же 10 golden-примерах не менее трёх раз.
3. Для каждого ответа автоматически проверить JSON Schema, категорию, срочность, source hit, полноту summary и ожидаемый режим `answer/clarify/escalate`.
4. Посчитать средний расход токенов, стоимость, p50 и p95 latency.
5. Отдельно проверить отсутствие статьи, неполные данные, длинную историю, сложное обращение, prompt injection и вредоносную вставку в документе.

Рабочая архитектура остаётся RAG + Structured Outputs: smoke-тест выбирает модель для следующей проверки, но не доказывает качество всей системы.
