# AI-часть: финальная документация LAB05

Версия runtime: `lab5-ai-engineer-categories-2026-11-20-r2`; точный commit и хеши
исходников/промптов/БЗ — [конфигурация финального опыта](../ml/experiments/lab5-category/evidence/followup/config.json).
Учебный сервис разбирает русскоязычные обращения в поддержку условного B2B SaaS.
Используются синтетические обращения и явно версионированные учебные процедуры.
Интерфейс имитирует helpdesk: подготовка ответа автоматизирована, реальной
внешней отправки, выдачи прав, возврата денег или удаления данных в нём нет.

## Последовательность обработки

```text
Событие/сообщение клиента + snapshot истории + точная версия KB
  → backend: доступ, схема, ограничение тела, новая версия обращения, очередь
  → immutable snapshot approved-статей этой версии
  → BM25: ранжирование совпадений по запросу и истории
  → Mistral: propose_card({card, assessment})
  → Python: схема, точные источники, ссылки на вход, полнота, секреты/риски
       ├─ обычный пригодный answer/clarify → подготовлено автоматически
       └─ ошибка/передача/неполное покрытие/готовый product_error → Sol
  → Sol: независимый разбор исходного обращения, истории и источников
  → те же проверки
       ├─ пригодный answer/clarify → подготовлено автоматически
       └─ нерешённая проблема/действие специалиста/отказ → ручная карточка
```

Проверенная защита входа, отсутствующая версия KB и исчерпание ресурсов могут
остановить разбор до генерации. Поэтому не каждое ручное состояние означает
два фактически состоявшихся сетевых вызова. Причина и этапы записаны явно.
Максимум одного обращения: две ступени, Mistral затем Sol, без бесконечных
LLM-циклов. Код, а не модель, решает, вызвать ли следующий провайдер.

## Модели и параметры

| Ступень | API-маршрут | Ограничения запроса |
|---|---|---|
| Mistral | api.mistral.ai, ministral-14b-2512 | temperature0, output≤1600, до 30 с; квота наблюдалась 2RPM/40kTPM, одна работающая попытка |
| Sol | apimira.com, openai/gpt-5.6-sol | reasoning_effort=low, output≤1600, до 45 с, input≤20000 по резерву |

Идентификатор Sol — маршрут провайдера ApiMira, а не прямое обращение к OpenAI.
Модель Mistral используется на подтверждённом участником Free-аккаунте.
Общий срок новой задачи 80 с включает ступени и технологический запас; worker
может сократить оставшееся время, если часть срока уже израсходована.
Новых платных автоматических повторов драйвер финального опыта не делает.

Основные runtime-файлы: [engine.py](../ml/cascade/engine.py),
[providers.py](../ml/cascade/providers.py), [assessment.py](../ml/cascade/assessment.py),
[retrieval.py](../ml/cascade/retrieval.py), [dialogue.py](../ml/cascade/dialogue.py).

## Поиск и база знаний

[KB](../ml/data/cascade/kb.jsonl) содержит v1, demo-20261112, support-20261112
и новую support-20261119. Последняя включает 10 статей: основные разделы плюс
диагностику неизвестного кода, повторной E42, расхождения оплаты и восстановления
2FA. Исторические 18 записей сохранены. Эти дополнительные процедуры — политика
учебного сервиса, а не проверенная документация неизвестного промышленного продукта.

Отбираются только status=approved и точное совпадение версии. В прототипе один
условный продукт; отдельного service_id/tenant ACL для статей нет. Нельзя
выдавать фильтр по версии за полноценное разграничение данных организаций.

**Фиксированного top-3 в runtime нет.** Mistral получает все лексические
совпадения в пределах технического окна. Для Sol статьи ранжируются и пакуются
целиком в предел 15904 байта всего JSON payload, с резервом для шаблона/выхода.
Есть одна фаза ограниченного доппоиска по новым подзапросам assessment;
Sol также может получить другие статьи pinned snapshot в пределах объёма.
Сохранены candidate_ids, included_ids, omitted_ids и payload_bytes.
Recall@3 в отчёте — диагностическая метрика поиска, а не лимит числа источников.
Отсутствующая статья не разрешает модели выдумывать процедуру или возможность.

## Единственный инструмент: propose_card

В tools API передаётся одна функция propose_card. tool_choice принудительно
выбирает её. Ответ API содержит аргументы функции; внешних действий функция
не выполняет. Python вызывает [execute_proposal](../ml/tools/propose_card.py),
проверяя точное разрешение propose_card, срок, схему и происхождение evidence.
Поиск, API следующей модели, БД и аккаунты инструментом модели не являются.

Аргументы внутреннего инструмента: `{card, assessment}`.
Схема инструмента строится [tool_schema](../ml/cascade/assessment.py).
Публичная карточка описана в [response.schema.json](../ml/contracts/response.schema.json).
request_id модель не задаёт: приложение добавляет доверенное значение,
попытка модели включить своё значение отклоняется.

| Поле card | Значение |
|---|---|
| mode | answer — готовый текст; clarify — полезный вопрос; escalate — специалист, draft_reply=null |
| category | access, payment, settings, integrations, product_error, other |
| summary, urgency, urgency_reason | Суть и обоснование срочности; самостоятельной gold-оценки urgency нет |
| known_facts, missing_data | Сведения с учётом источника и недостающее; нельзя приписывать клиенту действие |
| evidence | source_id/version/title и полный дословный excerpt применимой статьи |
| next_step | Непустой следующий шаг; текст формирует модель, а не таблица готовых ответов на каждый вопрос |
| draft_reply | Текст для клиента: действия/уточнение без служебных рассуждений о переданных статьях |
| status, needs_human_review | Модель предлагает proposed/true; только приложение может принять ordinary-карточку как resolved/false |

В assessment от 1 до 4 смысловых задач: id, question, input_quote только из
обращения/истории, coverage, source_ids, missing_customer_fields, answer_excerpt,
search_query и requested_fact. Покрытие complete/partial/missing/conflict
не является численной уверенностью модели. requested_fact — тип сведений:
error_code, error_message, observed_behavior, last_action, onset_time,
billing_period, billing_document, billing_amount, setting_name, notification_type,
other_customer_fact либо none. Название поля и сам вопрос свободные.
Похожие слова и валидная цитата сами по себе не доказывают смысловую правильность.

## Когда вызывается Sol

Ошибки формата/метаданных/проверок, неполное решение, reasoning_issue,
эскалация Mistral и выбранные важные случаи передаются Sol. **Готовый answer
категории product_error проверяется Sol всегда**, даже при валидном первом ответе.
Обычный пригодный clarify остаётся на Mistral. Подсчёта знаков «?» нет.

Sol получает исходный запрос, всю разрешённую историю, источники и при наличии
id/question/input_quote задач первой ступени. Draft Mistral, её confidence
или эталонные оценки в запрос Sol не передаются. Итог первой модели не
принимается за подсказку, которую нужно подтвердить.

## Диалог, cache и ручная карточка

Историю передаёт helpdesk/имитатор в новом snapshot. Backend сохраняет версии
входа; сам не достраивает отсутствующие сообщения. После нового сообщения
клиента начинается новая задача, снова с Mistral. Постоянной привязки к Sol,
автоматического обучения на одобренных ответах и обучения весов здесь нет.
dialogue_state выделяет ограниченные признаки, включая известный/недоступный
код ошибки по сообщениям клиента. Это подсказка, а не полная семантическая memory.
Известные сведения не следует спрашивать снова; повтор поведения всё ещё
возможен при ошибке модели и указан среди ограничений.

Cache ограничен 300 с/128 записей и включается явно. Ключ включает доверенную
область доступа, вход, контекст, схему, код и промпт. Только пригодный ordinary
answer допускается к хранению; при чтении результат проверяется заново.
В финальном живом eval cache выключен. Измерение cache hit проведено отдельно
на записанном валидном ответе, без новых сетевых вызовов.

При ручном разборе [backend/handoff.py](../backend/handoff.py) собирает исходный
вопрос, атрибутированную переписку, известные выполненные шаги, причины отказа
провайдеров и проверенные источники-кандидаты. Предварительные резюме моделей
показаны отдельно как требующие проверки. Гипотеза «клиент потерял код» не
становится фактом из одного вопроса о коде. При отказе обоих API технические
причины включаются в summary. Оператору доступны следующие шаги и отдельное
сохранение решения; клиентский draft при escalate пуст.

## Расходы, токены и наблюдаемость

API usage хранит фактические input/output и при наличии reasoning-токены.
Технический предел 20 млн — отдельный накопленный консервативный резерв
размера payload+шаблона+max output. Его нельзя выдавать за число потраченных
API-токенов. Денежная резервация Sol также не равна фактическому списанию.

Фактические расходы берутся из однозначно сопоставленного биллинга, в рубли
переводятся по 89 ₽/$. Неизвестное списание удерживает резерв. Один receipt
не применяется повторно. В [billing.py](../ml/cascade/billing.py) и очереди
есть проверка соответствия идентификатора/usage и idempotent-сверка.
Mistral RPM/одновременность и Retry-After учитываются durable-очередью.

Ключи берутся из окружения: MISTRAL_API_KEY, APIMIRA_API_KEY,
LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_BASE_URL. Их значений в
сдаваемом пакете нет. Необязательный доверенный CA задаётся через CASCADE_CA_FILE;
TLS и hostname-проверки не выключаются. Langfuse GENERATION связывается с
trace_id задачи. Тексты отправляются в трассу только при явном
TRACE_SYNTHETIC_CONTENT=true для синтетического набора.

## Воспроизведение и ограничения

[Пошаговые команды](../ml/experiments/lab5-category/README.md),
[финальные метрики](ml-final-metrics.md), [абляция и ноутбук](experiments/lab5.md).
Драйвер сохраняет конфигурацию, точный тег/commit, хеши, сырые ответы, этапы,
тайминги, расходы и проверку Langfuse. Повторное открытие ноутбука не оплачивает API.

Известные ограничения: малый известный development-набор; старые эталоны
местами отражают прежнюю политику; валидность JSON и цитат не доказывает
обоснованность причин; Mistral нестабильно возвращает assessment; Sol не
устраняет всякую ошибку; таймаут не доказывает отсутствие списания. Публичный
North Star и SLA из этих измерений не выводятся. Учебный snapshot не заменяет
проверку реальных процедур Product и независимую приёмку Quality.


## Обновление категорий и уточнений · 20.11

[category.py](../ml/cascade/category.py) отделяет проверку исходной схемы и
request_id от приёмки текста ответа. Backend повторно проверяет raw-карточки
с привязанным snapshot; последняя валидная классификация Sol или Mistral
сохраняется в содержательной ручной карточке и handoff.classification.
Ошибочный assessment и таймаут сами по себе не меняют тему на other.
Прежние risk-guards сохраняют тему явного инцидента без вызова модели.
Это происхождение классификации, а не подтверждение правильности советов.
Публичная схема не менялась; технический not_analyzed по-прежнему имеет other.

Для source-free clarify добавлены типы периода, документа, суммы, настройки
и писем. Одно уточнение может собирать до трёх связанных безопасных сведений.
Рекомендации действий, запросы секретов, полных реквизитов и роли по-прежнему
не принимаются как source-free уточнения. Обычный пригодный clarify остаётся
на Mistral; правила Sol и денежные лимиты не расширены.
