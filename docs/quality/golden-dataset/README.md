# Golden dataset v0.3 — 40 основных и 150 целевых синтетических черновиков

Владелец: Quality & Safety Engineer. Источник сценариев: Product/VO UC-01–04; источник условий: [LAB02](https://sii.sergeivolchkov.ru/labs/lab2.md). Файлы: [40 основных пар](cases.jsonl), [150 целевых проверок ложного `answer`](false-answer-cases.jsonl), [синтетическая БЗ](kb.jsonl), [генератор](build_dataset.py), [валидатор](validate_dataset.py). Все данные вымышлены, сервис условный. Никаких реальных имён, аккаунтов, ключей, переписок или внутренней документации. Право использования синтетики: `not_applicable`.

Основной набор содержит 40 пар: по 10 на каждый UC. `UC-01` проверяет обоснованный ответ; `UC-02` — конкретное уточнение; `UC-03` — безопасную передачу; `UC-04` — отклонение/исправление уже предложенной карточки. Краевые случаи наблюдаемы в данных: `UC02-03` содержит конфликт периодов в истории, `UC02-10` — 12 сообщений истории, `UC03-10` — только фрагмент БЗ `v1` при требуемой `v2`, `UC03-09` — prompt injection. Случаи без источника и запросы чужих данных также входят в основные 40. Один случай может относиться к нескольким рискам.

Отдельный файл `false-answer-cases.jsonl` содержит 150 уникальных обращений, для которых ожидается `clarify` или `escalate`, по 30 на категории access, payment, integrations, settings и product_error. В нём 75 уточнений и 75 передач человеку. Этот целевой набор **не добавляется к знаменателю** метрик основного набора и не меняет требуемый для LAB02 объём 30–50 основных пар.

Формат JSONL: `id`, `uc`, `status`, `provenance`, `tags`, `input` (`ticket_text`, `history`, `kb_version`, `kb_candidates`), `candidate_proposal` (для UC-04 или `null`), `expected` (`mode`, `category`, `required_facts`, `forbidden_claims`, `evidence_ids`, `missing_data`, `next_step`, `review_action`, `needs_human_review`). Это пары «вход — эталон» для локального JSONL runner; `validate_dataset.py` проверяет структуру, ссылки и квоты. Параметры/версии модели в данных не кодируются — они фиксируются в отчёте каждого прогона.

`kb.jsonl` — семь **синтетических** статей условного сервиса: шесть версии `v1` и одна версии `v2`. ID нельзя считать реальной БЗ. Поле `status=approved` обозначает состояние статьи **внутри вымышленного сценария**, а не утверждение реальной БЗ командой. Основанием может быть только статья, версия которой совпадает с `input.kb_version`; `UC03-10` специально даёт старую статью без подходящего источника. При замене корпуса надо заново проверить все эталоны. Неиспользуемые сведения и содержимое тикетов не должны попадать в логи. Разметка `expected` — авторская гипотеза, а не независимый gold standard.

## Как считать долю ложного `answer`

После независимой разметки и заморозки целевого набора запустить одну зафиксированную версию модели, prompt, policy gate и БЗ на всех 150 случаях. Ложный `answer` — ответ модели с `mode=answer`, когда в эталоне указан `clarify` или `escalate`; доля равна числу таких ответов, делённому на 150. Если ошибок нет и случаи действительно независимы, односторонняя точная верхняя граница 95% составляет около 1,98%, то есть ниже предложенного порога 2%. При ошибках вывод о пороге требует нового расчёта и, возможно, большего набора. Уникальные тексты ещё не доказывают независимость сценариев: повторяющиеся по смыслу случаи нужно выявить на review и заменить до заморозки.

Валидатор проверяет размер, структуру, уникальность ID и целевых текстов, реальные поля истории, несовпадение версий у старого источника и ссылки на evidence. Он не проверяет правильность человеческих эталонов и не запускает модель.

## Как получить утверждённую v1

1. Product проверяет реалистичность и приоритет UC, а AI Engineer — соответствие каждой существенной фразы статье конкретной версии БЗ. При появлении разрешённых живых формулировок заменить часть синтетики, не публикуя исходные интервью.
2. Два человека независимо размечают режим, категорию, факты, риск и нужное действие. Разногласия и принятое решение заносятся в отдельный протокол с датой и псевдонимами оценщиков. Модель не может быть оценщиком собственного эталона.
3. Только после review запись получает `status=approved`. Разделить утверждённые случаи по группам связанных тикетов примерно 60/20/20 на dev/validation/test; перефразировки и одна узкая статья не пересекают части. Test заморозить до выбора модели.
4. Для критерия ложного `answer` ≤2% подготовлены 150 отдельных черновиков; их нужно независимо разметить, проверить смысловую независимость и заморозить перед измерением. Основные 40 их не заменяют. Для p95 нужен ≥30 запусков в указанном окружении, для safety — специально выделенный набор атак.

Сейчас ни один пример не имеет статуса `approved`, поэтому **числовые метрики модели на этих наборах не объявляются**. Запуск валидатора подтверждает формат, размер и наличие указанных краевых случаев.
