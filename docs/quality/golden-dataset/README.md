# Golden dataset v0.2 — 40 синтетических черновиков

Владелец: Quality & Safety Engineer. Источник сценариев: Product/VO UC-01–04; источник условий: [LAB02](https://sii.sergeivolchkov.ru/labs/lab2.md). Файлы: [cases.jsonl](cases.jsonl), [kb.jsonl](kb.jsonl), [генератор](build_dataset.py), [валидатор](validate_dataset.py). Все данные вымышлены, сервис условный. Никаких реальных имён, аккаунтов, ключей, переписок или внутренней документации. Право использования синтетики: `not_applicable`.

40 пар: по 10 на каждый UC. `UC-01` проверяет обоснованный ответ; `UC-02` — конкретное уточнение; `UC-03` — безопасную передачу; `UC-04` — отклонение/исправление уже предложенной карточки. Краевые случаи включают устаревшую статью, противоречивые факты, длинную историю, отсутствие источника, просьбу о чужом аккаунте и инъекции. Один случай может относиться к нескольким рискам.

Формат JSONL: `id`, `uc`, `status`, `provenance`, `tags`, `input` (`ticket_text`, `history`, `kb_version`, `kb_candidates`), `candidate_proposal` (для UC-04 или `null`), `expected` (`mode`, `category`, `required_facts`, `forbidden_claims`, `evidence_ids`, `missing_data`, `next_step`, `review_action`, `needs_human_review`). Это пары «вход — эталон» для локального JSONL runner; `validate_dataset.py` проверяет структуру, ссылки и квоты. Параметры/версии модели в данных не кодируются — они фиксируются в отчёте каждого прогона.

`kb.jsonl` — **синтетические** статьи условного сервиса; ID нельзя считать реальной БЗ. Только `approved` версии могут служить основанием. При замене корпуса надо заново проверить все эталоны. Неиспользуемые сведения и содержимое тикетов не должны попадать в логи. Разметка `expected` — авторская гипотеза, а не независимый gold standard.

## Как получить утверждённую v1

1. Product проверяет реалистичность и приоритет UC, а AI Engineer — соответствие каждой существенной фразы статье конкретной версии БЗ. При появлении разрешённых живых формулировок заменить часть синтетики, не публикуя исходные интервью.
2. Два человека независимо размечают режим, категорию, факты, риск и нужное действие. Разногласия и принятое решение заносятся в отдельный протокол с датой и псевдонимами оценщиков. Модель не может быть оценщиком собственного эталона.
3. Только после review запись получает `status=approved`. Разделить утверждённые случаи по группам связанных тикетов примерно 60/20/20 на dev/validation/test; перефразировки и одна узкая статья не пересекают части. Test заморозить до выбора модели.
4. Для критерия ложного `answer` ≤2% нужен **отдельный** размеченный набор ≥100 случаев; нынешние 40 его не заменяют. Для p95 нужен ≥30 запусков в указанном окружении, для safety — специально выделенный набор атак.

Сейчас ни один пример не имеет статуса `approved`, поэтому **числовые метрики модели на этом наборе не объявляются**. Запуск валидатора подтверждает лишь качество формата и покрытие сценариев.
