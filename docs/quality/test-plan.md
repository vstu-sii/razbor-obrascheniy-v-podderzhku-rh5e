# Тест-план LAB02 → CI LAB03

Единица оценки — одно обезличенное обращение с историей, версией БЗ и ожидаемым следующим шагом. План основан на Product UC-01–04 и проекте AI API. До подключения реального сервиса тестируем контракт и заглушки, а не заявляем производственные метрики.

| Уровень | Что проверяется | Данные / оракул | Когда |
|---|---|---|---|
| Unit | Валидация схемы, словари, лимиты входа, `answer` только с годным evidence, один retry, отказ от auto-send | синтетические фикстуры и ожидаемые ошибки | каждый PR с LAB03 |
| Integration | UI/backend/AI/БЗ/DB: UC-01–04, 503/timeout, пустая/устаревшая БЗ, отдельное хранение proposal/review | тестовый Compose и sandbox helpdesk с подсчётом write-вызовов | PR + nightly |
| Contract | OpenAPI response/error, поле `needs_human_review=true`, идентичные category/mode в AI и UI | валидатор OpenAPI и ответы заглушки/реального AI | каждый PR |
| Security | тикет, история, статья БЗ и feedback как недоверенные тексты; запрет утечки и действий без человека | safety cases из golden + атаки из threat model | PR smoke, расширенно LAB04 |
| Evals | mode/category/grounding/полнота/тон/пригодность, ложный `answer`, Recall@3, цена, p95 | только `approved` freeze версии набора; два оценщика для субъективного | перед выбором модели и релизом |

**Автоматический CI с LAB03:** синтаксис/линт, JSONL-schema и квоты, unit, OpenAPI contract, build Compose, smoke `/health`, негативный тест «proposal/reject не пишет в helpdesk». Полные модельные evals с внешним API и реальными ключами не запускаются на каждом публичном PR: секреты — только защищённый runner, данные — только разрешённые. CI должен явно различать smoke и eval, чтобы зелёный build не трактовался как качество модели.

**Измерение:** на фиксированном утверждённом наборе считать долю пригодных карточек; режим `answer` без подтверждённого источника — отдельный блокирующий счётчик. p95 от начала анализа до готовой карточки по ≥30 обращениям с указанием окружения. Цена включает токены, retrieval, embeddings и повторы. На ≥100 отдельных кейсах оценивать долю ложного `answer`; на 30 кейсах допускать 0. Замеры повторяются при изменении модели, prompt, БЗ или policy gate.

**Дефект и выпуск:** критическая утечка/опасный совет/автоотправка блокируют выпуск до исправления независимо от средней метрики. Исправление сопровождается regression case, но текущие тестовые `draft_synthetic` не дают права объявить порог достигнутым.

## Событийная архитектура, уточнение 26.10.2026

Разбор запускают события `ticket.created` и `customer.message_received`, а не кнопка оператора. Подробные сценарии и ожидаемые результаты: [проверки событийной обработки](test-plan.md#сценарии-событийной-обработки). EVT-01–14 пока являются планом, успешный runtime-прогон не заявлен.

Unit: правила допуска событий, расчёт оставшихся попыток и бюджета. Contract: поля события и ответы 4xx/503. Integration: PostgreSQL, атомарная запись, дедупликация, lease, рестарт и два исполнителя. Сквозные проверки: событие → очередь → карточка → отдельный review. Security: подпись, права на тикет, повторная доставка и перегрузка.

В CI проверяются план и формат доказательств. Полный runtime-порог должен требовать успешного выполнения всех сценариев на версии с очередью; пока он не выполнен. Исторические модельные evals остаются отдельной проверкой. Время от события включает очередь; прежняя latency модели не используется вместо него. Общий лимит двух вызовов включает вложенные повторы и рестарты, deadline задачи — 55 секунд.

## Сценарии событийной обработки

Содержательные evals модели и транспортные проверки разделены. Набор из 40 примеров Q-002 сохраняет исходные входы и эталоны. Инфраструктурные сценарии не увеличивают число модельных примеров.

| ID | Воздействие | Ожидаемый результат |
|---|---|---|
| EVT-01 | ticket.created | Одна задача, карточка без кнопки запуска |
| EVT-02 | Повтор того же event_id | Одна запись события и одна задача |
| EVT-03 | Разные event_id одной версии | Дедупликация по тикету и версии |
| EVT-04 | Новая версия при queued | Одна ожидающая задача последней версии |
| EVT-05 | Новая версия при running | Один активный разбор, одна ожидающая версия, старый результат не становится актуальным |
| EVT-06 | Подтверждение одновременно с сообщением клиента | Атомарная проверка версии, устаревший ответ не отправляется |
| EVT-07 | Просмотр, заметка, статус, review | Ноль новых задач и вызовов модели |
| EVT-08 | Достигнут MAX_RUNNING | Параллельность ограничена, остальные задачи ожидают |
| EVT-09 | Достигнут MAX_PENDING | Retryable 503 до подтверждения события, успешная повторная доставка после освобождения; уже известный дубль подтверждается и при полной очереди |
| EVT-10 | Исчерпаны частота или токены | Запуск отложен, резерв сохранён |
| EVT-11 | Падение исполнителя после вызова | Попытки не обнуляются, суммарно максимум два вызова, включая вложенные повторы AI-адаптера |
| EVT-12 | Неверная подпись, тип, размер, чужой тикет | Отказ до записи и вызова модели, секретов в логах нет |
| EVT-13 | Исчерпан deadline или повторы | manual_review с причиной, без клиентского черновика |
| EVT-14 | UC-01–04 на готовой карточке | Источники, режим и отдельное решение оператора сохранены |

### Статус проверки

Это план технической приёмки, а не протокол успешного прогона. Все EVT-01–14 ожидают проверки на реализации очереди. Исторический baseline генерации не проверяет webhook, очередь, версии, рестарт и отправку. Подтверждение пользовательских UC не заменяет эти технические проверки.

### Измерения и DoD
Для каждого сценария фиксируются вход, конфигурация, ожидаемый и фактический результат, число задач и модельных вызовов. Аварийные сценарии включают состояние после рестарта. Время до карточки считается от приёма события, отдельно измеряются ожидание и latency модели. Сохраняются event_id, версия тикета, число попыток и состояние. Лимиты очереди, частоты, параллельности и токенов задаются конфигурацией. Для runtime-доказательства указываются версия приложения, окружение, конфигурация и trace/лог. Проверяются одновременные исполнители и задержка в очереди, а не только один процесс. Общий deadline 55 секунд и максимум два вызова действуют на всю задачу, включая рестарты.

### Угрозы
Повтор webhook и шквал событий расходуют бюджет. Контроли: проверка подписи, дедупликация, общий rate limit, конечная очередь и резерв до вызова. Подмена ticket_ref не должна раскрывать чужую историю. Событие старой версии не откатывает текущую карточку. Review не запускает inference. Тексты клиента и БЗ остаются недоверенными данными.

### Ответственность
Delivery отвечает за очередь, lease, транзакции и актуальность. AI Engineer отвечает за общий лимит попыток, расход и безопасный отказ. Quality ведёт сценарии и доказательства результата. Product определяет смысл UC и действие оператора. Повторное прохождение пользовательских UC подтверждено участником 23.10.2026. Эти сценарии задают техническую приёмку новой архитектуры.
